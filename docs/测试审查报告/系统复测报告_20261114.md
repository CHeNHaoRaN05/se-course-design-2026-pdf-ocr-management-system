## 为什么 0 审批也能合并（分支保护配置核查）

`protect-main` ruleset（id `25813280`，2026-10-25 创建，`enforcement=active`，条件 `~DEFAULT_BRANCH` 即 `main`）确实存在，`bypass_actors=null`（无绕过名单），含 `deletion`、`non_fast_forward`、`pull_request` 三条规则。规则是生效的：黄没有直接 push `main`，而是开了 PR #10 再合并。

放行原因是 `pull_request` 规则的参数本身允许 0 审批：
- `required_approving_review_count=0`；`require_code_owner_review=false`；`required_reviewers=[]`
- `require_last_push_approval=false`、`dismiss_stale_reviews_on_push=false`、`required_review_thread_resolution=false`
- 规则集中没有 `required_status_checks`，CI 通过不是合并前置条件（本次恰好全绿）
- `allowed_merge_methods=[merge,squash,rebase]`

PR #10 `user=smile4180`、`merged_by=smile4180`（同一人自开自合），`reviews=0`，事件时间线仅 `committed → merged → closed`。因此不是绕过规则，是 GitHub 按配置放行。

`.github/CODEOWNERS` 三重失效（`main` 与工作区版本一致）：
1. 路径前缀写成 `/backend/`、`/frontend/`，仓库根并无这两个目录，实际代码在 `pdf_system/backend/`、`pdf_system/frontend/`；仅 `/docs/`、`/pdf_ocr_module/`、`/README.md`、`/.github/` 可匹配。
2. 规则中的 owner 与注释里的 GitHub 账号不一致，且部分账号不存在：`@yuehaorui`→404、`@zhimengshusi`→404、`@yuehaorui.1`→404；`@chenhaoran`/`@huangyufu`/`@CHeNHaoRaN05`/`@smile4180`/`@smile1810` 可解析但归属未核实。真实提交作者为 `陈浩然`、`yuehaorui.1`、`smile4180`。
3. 即使路径与账号都修好，`require_code_owner_review=false` 仍使 CODEOWNERS 不阻塞合并。

PR #10 共 58 个文件，其中 12 个落在共享所有权路径：`pdf_system/backend/core/{config,file_cleanup,security}.py`、`main.py`、`modules/{auth,quota,files,search,audit}/...`。按 `CONTRIBUTING.md` 与 CODEOWNERS 本应触发 01/02 线评审，实际 0 review。

该仓库为个人账号所有（owner `CHeNHaoRaN05`，非组织），GitHub 的 `required_reviewers`（指定团队审批）在此类仓库不可用；要把审批绑定到特定人，只能靠 CODEOWNERS + `require_code_owner_review`。

## 改成「必须经我审批才能合并」的配置方案

前提：先确认自己的 GitHub 登录名且有仓库写权限。仓内现有 `CHeNHaoRaN05`（仓库 owner）、`smile4180`、`smile1810` 可解析；`yuehaorui`、`yuehaorui.1`、`zhimengshusi` 返回 404，`chenhaoran`、`huangyufu` 虽 200 但归属未核实，不能直接当审批人写进 CODEOWNERS。

1. 网页路径：`Settings → Rules → Rulesets → protect-main`，编辑 `Require a pull request before merging` 并展开 `Additional settings`，把以下项改掉：
   - `Required approvals` `0 → 1`（若要求两人审批可设 `2`）。
   - 勾选 `Require review from Code Owners`（`require_code_owner_review=true`）——这是把审批绑定到「我」的关键，`required_approving_review_count` 本身只要求任意有写权限的人批准。
   - 勾选 `Dismiss stale pull request approvals when new commits are pushed`、`Require approval of the most recent reviewable push`、`Require conversation resolution before merging`，防止审批后追加提交绕过。
   - `Bypass list` 保持为空（当前 `bypass_actors=null`），不要给 Repository admin / 任何人加绕过，否则规则可被跳过。
   - 新增 `Require status checks to pass before merging`，添加 `backend-tests`、`frontend-build`（PR #9 合并后再加 `frontend-integration`），使 CI 成为硬门槛而非巧合通过。
2. 修 `.github/CODEOWNERS`，否则 `require_code_owner_review` 仍然形同虚设：
   - 路径必须带真实前缀，例如 `/pdf_system/backend/core/`、`/pdf_system/backend/main.py`、`/pdf_system/frontend/src/app/`、`/pdf_system/frontend/src/shared/`、`/pdf_system/backend/modules/files/`、`/pdf_ocr_module/`、`/docs/`；现在的 `/backend/`、`/frontend/` 匹配不到任何文件。
   - owner 换成真实且对仓库有写权限的账号；CODEOWNERS 中同一路径被多条规则匹配时**最后一条生效**，所以若想全部改动都经我审批，应在**每一条**规则里都写上 `@<我的账号>`，并在文件最末尾加一行兜底 `* @<我的账号>`。
   - 同一路径列多个 owner 时任一人批准即满足，因此要求「必须经我」的路径不要并列其他账号。
3. 已知限制：PR 作者不能批准自己的 PR。若「我」是唯一 code owner，则自己开的 PR 会死锁。可选做法是保持由组员开 PR、我来审批；或增设第二名 code owner；或仅给本人登记 bypass actor（会留下无审批合并记录，需权衡）。个人仓库无 team 机制，无法用 `required_reviewers` 指定「仅我」。
4. 可选更严格：把另外两名组员的仓库权限降为仅能推送分支、不能合并 PR；个人仓库没有「仅指定用户可合并」的原生分支规则，最可靠仍靠第 1、2 步组合。
5. 生效验证：新建测试分支开一个改动 PR，确认未审批时 Merge 按钮被禁用并提示所需审批；用另一账号 approve 后仍应提示需要 code owner 审批；再由本人 approve 才解锁。改完复查 `GET /rulesets/25813280` 与 `GET /rules/branches/main` 的返回值。
