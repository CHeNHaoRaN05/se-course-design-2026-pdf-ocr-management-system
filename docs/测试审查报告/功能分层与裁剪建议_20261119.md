# 功能分层与裁剪建议（2026-11-19，聚焦文档上传/下载/显示/管理）

背景：进度落后，把有限时间集中在**文档的上传、下载、显示、管理**四件事上；配额、统计、审计、OCR 高级能力等一律降级或砍掉。
依据：`docs/features.md`、`docs/team/backend.md`、main 与 PR #9 的实际路由/前端代码、既有实机审查。

## 一、最重要结论：先合 PR #9

按这四块核对 main 与 PR #9，**关键缺口几乎都在未合并的 PR #9 里**：

| 能力 | main 现状 | PR #9（`5f5eb76`）现状 |
|---|---|---|
| 上传 | `POST /files`，三重校验，有 | 同左，且并发同名 + 边界修复 |
| **下载原文件** | **无**。后端只有 `GET /files/{id}/content`（`inline` 内联，供 pdf.js 用），前端 `filesApi` 没有下载方法，`features/files`、`reader`、`management` 里无任何「下载」入口 | **有**：`FilesPage.tsx:144,177,761`「下载原文件」按钮 + `fileBlob()` + `downloadBlob()`；分享文件也走 `allow_download` 旁路 |
| 显示 | pdf.js 渲染/缩放/翻页/按页尺寸，书签批注增删查；缩略图与页内搜索是 W7 占位 | 与 main 完全相同（未增强阅读器） |
| 管理 | 重命名、文件夹、标签、软删、回收站、还原、彻底删除 | **额外有** `/files/query`（带 total、状态过滤）、`/trash` 分页、`/files/bulk`（批量删/移动/打标）、`merge`/`split`、管理页与分享管理页 |

结论：**「下载」这个最基础能力当前 main 不具备，且代码已写好卡在 PR #9**。合 PR #9 是唯一能在半天内补上下载 + 批量 + 管理页的动作，且它 CI 4 job 全绿（含 windows-latest e2e 35/35、test:live 通过）。

## 二、按四块重排的功能分层

### 最基础（必须保住，答辩底线）

| 块 | 功能 | 现状 / 动作 |
|---|---|---|
| 上传 | PDF 上传（扩展名 + MIME + 魔数三重校验、大小/页数上限、同名序号） | main 有，保留 |
| 上传 | 并发同名、超长 q、naive 过期等边界修复 | 在 PR #9，随合并带入 |
| 下载 | **登录用户下载原文件按钮** | **PR #9 有，main 无** → 合 PR #9 |
| 下载 | 分享者凭 token + 提取码下载（`allow_download`） | main 有，保留 |
| 显示 | PDF 在线预览（pdf.js 渲染、缩放、翻页、跳页）、按页尺寸、Range 请求 | main 有，保留 |
| 显示 | 书签 / 批注 增 / 删 / 查 | main 有，保留 |
| 管理 | 列表、详情、重命名、文件夹、标签、软删除、回收站、还原、彻底删除 | main 有，保留 |
| 管理 | 管理分页（total、状态过滤）、批量操作、合并 / 拆分 PDF | **PR #9 有，main 无** → 合 PR #9 |

### 中级（加分，有余量再做）

- 阅读器：缩略图侧栏、目录大纲、页内搜索与高亮（`ReaderPage.tsx:79` 自注 W7 待补）
- 阅读器：OCR 文本层叠加（可选中复制）、阅读位置记忆、批注修改/撤销
- 管理：文件版本与代次（当前仅有 `version`/`replaced_from` 字段，无版本列表与回滚）
- 管理：独立分类树（≤5 级、禁环、标签颜色；当前 `folders` 只是字符串去重）
- 下载：导出结果的 CSV/HTML/XLSX（当前 main 有 TXT/JSON/CSV/HTML/XLSX 五种，但依赖 OCR 结果；若 OCR 不演示可整体砍）
- 账号：管理员改角色、账号禁用、改密、令牌续期（main 有，保留但不投入新工时）

### 高级拓展（砍掉或延期）

- **配额管理**（写接口、容量上限、超额拦截、统计页）：砍前端与写接口；底层 `ocr_before_enqueue` 默认空实现 + `settle_terminal` 独立账本必须保留，否则 OCR 任务结算回归
- **统计看板**（成功率、平均耗时、存储占用、按日聚合）、**审计日志 180 天保留作业**：砍
- **OCR 识别 / 校对 / 表格还原 / 全文检索**：从"必演示"降为"可选演示"。理由：真实 Paddle 链路未跑通（`evaluate.py` 的 `accuracy_acceptance_passed=None`，8 skip 含 1 项真实 OCR），且这些不属于本次重点
- 200 页准确率评测、10 万页 P95、生产部署与恢复演练：砍
- 阅读器 OCR 文本层、检索过滤/历史、语言/方向检测、手写模式、流式导出、校对撤销：砍

## 三、执行顺序（按这四块）

1. **合 PR #9**（或至少摘取 `FilesPage.tsx` 的下载按钮 + `management.py` 的 `/query`、`/bulk`、`/merge`、`/split`）——补上 main 缺失的下载与管理能力。合之前先修 CODEOWNERS 路径/账号与 `required_status_checks` 门禁，并要求 01/03 线对跨线文件批准（PR #9 触及大量 01/03 所有文件）。
2. **验收四块主流程**（可在无 Paddle 权重的环境下做）：注册登录 → 上传 PDF → 列表/管理页查看（total、过滤）→ 打开预览/翻页 → 下载原文件 → 重命名/打标/批量移动 → 软删 → 回收站还原 → 合并/拆分 → 分享下载。
3. **修 Windows 短名路径下 `safe_path` 并发误抛 `invalid_storage_key`**（否则 CI Windows 矩阵必红，影响上面的交付可信度）。
4. 有余量再按中级清单补阅读器缩略图/目录/页内搜索；OCR 相关仅在老师明确要求时再投入。

## 四、裁剪风险提示

- 砍配额 UI 时不要删 `ocr_before_enqueue` 默认实现与 `settle_terminal`；砍分享限速后需在文档标注访客接口无速率限制。
- 把砍掉的功能在需求追踪矩阵标注「范围调整/延期」而非「已实现」。
- 若最终完全不演示 OCR，应在交付说明中明确"本项目当前交付范围为文档上传/下载/显示/管理"，避免与需求文档中 OCR 为核心卖点产生落差——这一口径需先与老师确认。
