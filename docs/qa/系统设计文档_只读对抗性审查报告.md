## 0. 结论摘要

| 维度 | 评级 | 判断 |
|:---|:---|:---|
| 与项目真实情况符合性 | **中等偏高，但不均匀** | 架构、进程划分、队列/租约/CAS、乐观锁、ngram 索引、代次、导出安全、C1～C5 契约等**核心机制描述准确**；偏差集中在「环境配置、前端集成状态、运维能力」三类，共发现 **13 项事实性错误** |
| 标准设计文档充分性 | **对「概要设计」充分甚至过载，对「工程基线」不足** | 缺接口详细规格、测试设计、监控采集口径、风险登记与未决问题清单；章节归属存在错配 |
| 表述专业性 | **整体专业，但三态标记不统一** | 6.4 明确写「以上为设计目标」，而 6.1/6.2/6.3/4.3 把同类未实现项写成既成事实，是最大专业性缺陷 |
| 冗余度 | **偏高** | 环境/端口/版本、错误模型、四层映射、原则-约束-决策三表均有 3～5 轮重复 |

**总体判断**：这是一份结构完整、工程语感明显优于一般课程设计文档的 SDD，可直接作为评审材料；但**不能作为「与代码一致的验收基线」使用**——文档把原型界面、设计目标与已落地实现混写，且若干硬事实（权重路径与体积、主键规则、配置注入、测试数量、前端请求出口）与代码相悖。建议先做「三态标注统一」再修事实错误，最后做结构重组与去重。

## 4. 文档优点（避免单边结论）

1. **工程诚实性已部分具备**：6.4 明确「以上为设计目标，尚未完成实测」、表 2-6 列「尚未验证」、表 6-7 主动列出 P0 MySQL 条件更新缺陷与 P1/P2/P3 待办——这在同类文档中少见。问题不是「不诚实」，而是**这套标注没有贯穿全文**。
2. **核心机制描述与实现高度一致**：进程划分与同进程挂载、数据库表即队列（租约 + CAS + `SKIP LOCKED`）、页级 `revision` 乐观锁、ngram `ddl_if` 与 SQLite LIKE 降级、5 种导出与公式注入防护、归一化 bbox、C1～C5 五份契约，均经代码逐项确认为「符合」。
3. **架构决策表（表 3-4）含「理由 / 代价」双列**，具备真实权衡，而非方案罗列。
4. **编号与索引体系完整**：39 张图号连续、55 张表编号连续、附录 B 图索引可定位、附录 A 覆盖全部 FR/NFR 组。
5. **数据设计充分**：16 表数据字典、JSON 结构、索引清单、状态枚举、完整性约束、容量与保留策略齐备，超出一般概要设计要求。
