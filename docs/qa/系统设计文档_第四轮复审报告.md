## 一、总体结论

前三轮处理的三态标注、NFR 追踪矩阵、接口状态语义、数据字典字段说明等，本轮抽查未发现回归。本轮换角度后，**未发现新的 P0 事实错误**，核心数字与实现大体经得起复核（详见第二节）。

但发现 **3 项 P1**：一处文档内部版本口径自相矛盾、一处"部署一致性"把实现的自动注入机制写成人工约定、一处真实存在的 JWT issuer/audience 部署陷阱（改配置即导致 OCR 侧鉴权失败，而文档的一致性清单未列该项）。另有 **4 项 P2**（配置清单不足以支撑部署、规模假设依据链缺中间变量、附录 B 通配符索引不可逐图定位、Word 正稿图片超宽且静态目录无页码）与 **3 项 P3**。

结论：文档作为**设计约定基线**已可用；若作为交付/部署依据，需先收口 N4-01～N4-03，否则部署方会按文档做出与实现相反的操作。前三轮提出的扩写型充分性缺口（接口逐条详细规格、独立测试设计章节、监控采集口径、风险登记表、文档定位由"概要设计"改为"详细设计"）本轮不重复展开，仍未解决。

## 三、问题清单

### P1：契约 / 部署口径风险

**N4-01　文档内部 Python 版本口径冲突（自相矛盾）**
- 位置：`:241`（表 2-6 版本约束）与 `:1175`（6.4 兼容性设计）
- 证据：`:241` 写"Worker 所在 Python 环境 **≤ 3.13**（Paddle 3.0.0 无 cp314 wheel）……3.13 尚无实测记录；两侧 Python 版本允许不同"；`:1175` 写"主系统 API 以 Python 3.12 为基线，3.14 需切换备用依赖版本组，**Worker 固定 3.12**"。
- 判定：一处允许 Worker 用 3.13（仅声明未实测），另一处把 Worker 锁死在 3.12；且 `:1175` 与 `:241` 的"3.14 需按 `requirements.txt` 备用版本组安装"措辞亦不统一（一侧允许 3.14 主系统，另一侧删去了这一条件）。
- 影响：部署与验收环节无法确定 Worker 的可用版本集合；若按 `:1175` 执行，`:241` 的"两侧 Python 版本允许不同"实际上被收回。
- 建议：统一为"主系统 API 以 3.12 为基线，3.14 可按备用版本组安装；Worker 经验证环境为 3.12，≤3.13 为理论可用上界，3.13 未实测、3.14 因无 cp314 wheel 不可用；两侧版本允许不同"，并删去"固定 3.12"。

**N4-02　"部署一致性要求"与实现的注入机制不符（会误导部署操作）**
- 位置：`:1085`（6.1 部署一致性要求）、`:1099`（表 6-2 说明）、表 6-2（`:1091-1093`）
- 证据：`pdf_system/backend/core/config.py:51-58` 定义 `ocr_env()` 导出 `OCR_DATABASE_URL` / `OCR_STORAGE` / `OCR_JWT_SECRET` / `OCR_DEVICE` 四项；`backend/modules/ocr/mount.py:34-35` 在挂载前执行 `os.environ[key] = value  # 覆盖，避免遗留环境变量造成两侧漂移`；`backend/scripts/init_db.py:24-25` 同样注入。
- 判定：实现是**主系统单向注入并强制覆盖**，文档却表述为"主系统与 OCR 侧**必须使用**同一数据库、同一存储目录、同一 JWT 密钥"，并把 `OCR_*` 与 `PDF_*` 并列为需配置的变量，读起来是"部署方两侧各配一遍、人工保证一致"。
- 影响：部署方若按文档手工设置 `OCR_DATABASE_URL` 等，运行时会被静默覆盖，故障排查方向被误导；6.5 表 6-8 的"典型症状"也缺少这一条。
- 建议：改写为"主系统在挂载 OCR 模块（及初始化数据库）前由 `ocr_env()` 覆盖写入四项 OCR 侧配置，部署方只需配置主系统侧 `PDF_*`；手工设置的同名 `OCR_*` 不会生效"，并把表 6-2 的四项标注为"主系统注入，非部署项"。

**N4-03　JWT issuer / audience 一致性缺口（真实部署陷阱，前三轮未覆盖）**
- 位置：`:1085` 部署一致性清单、表 6-2（`:1093`）
- 证据：`backend/core/config.py:28-29` 的 `jwt_issuer` / `jwt_audience` 是 `PDF_*` 可覆盖字段；`ocr_service/config.py:19-20` 将其写为**硬编码常量** `"pdf-system"` / `"ocr-api"`；`ocr_env()`（`config.py:53-58`）**不注入**这两项；`ocr_service/auth.py:22` 以 `issuer=cfg.jwt_issuer, audience=cfg.jwt_audience` 校验令牌。
- 判定：只要部署方按运维惯例修改 `PDF_JWT_ISSUER` 或 `PDF_JWT_AUDIENCE`，主系统签发的新 claim 与 OCR 侧校验常量不匹配，跨模块调用（契约 C1）即鉴权失败；而文档的一致性清单只列"同一数据库、同一存储目录、同一 JWT 密钥"三项，未提示该约束。
- 影响：属于"配置一改就坏、文档无排查依据"的隐蔽耦合，比缺一个配置项严重。
- 建议：在部署一致性要求中补"两侧 `jwt_issuer` / `jwt_audience` 必须一致；OCR 侧当前为代码常量，调整主系统侧相应环境变量须同步修改 OCR 配置模块并重新部署"。若后续决定把两项加入 `ocr_env()`，属于代码改动，本报告不代替实施。

### P2：专业性与内容充分性

**N4-04　表 6-2 配置项清单不足以支撑部署**
- 位置：`:1087-1099`
- 证据：主系统真实可配字段 17 个（`PDF_APP_NAME`、`PDF_API_PREFIX`、`PDF_DATABASE_URL`、`PDF_DATABASE_ECHO`、`PDF_JWT_SECRET`、`PDF_JWT_ISSUER`、`PDF_JWT_AUDIENCE`、`PDF_JWT_EXPIRE_MINUTES`、`PDF_STORAGE_DIR`、`PDF_MAX_UPLOAD_BYTES`、`PDF_MAX_PAGES`、`PDF_MAX_PIXELS`、`PDF_MONTHLY_PAGE_QUOTA`、`PDF_OCR_ENABLED`、`PDF_OCR_PACKAGE_DIR`、`PDF_OCR_STORAGE`、`PDF_OCR_DEVICE`），表 6-2 仅覆盖 5 个。其中 `PDF_OCR_ENABLED`、`PDF_OCR_PACKAGE_DIR` 直接决定 6.1"运行降级"是否发生（`mount.py:25`、`:29` 按这两项判定是否挂载），却未列入。OCR 侧另有 5 个可选环境变量未列：`OCR_DET_WEIGHTS`、`OCR_REC_WEIGHTS`、`OCR_CUSTOM_REC_WEIGHTS`、`OCR_HANDWRITING_WEIGHTS`、`OCR_TORCH_PYTHON`（`ocr_service/config.py:22-26`）。
- 需公允说明：`:1099` 的"OCR 侧仅四项由宿主注入"与 `ocr_env()` 一致、"上传上限等为代码常量"亦与代码一致，**这两句不是事实错误**；问题在清单的完整性，以及"由谁注入"未被区分（并入 N4-02）。
- 附带提示：`OCR_HANDWRITING_WEIGHTS` / `OCR_CUSTOM_REC_WEIGHTS` 是预留权重钩子，与 `:168`"不实现手写体专项识别"不冲突，但宜在边界句注明"预留配置项不构成功能交付"，避免读者据配置反推功能已实现。
- 建议：把表 6-2 重组为"必须配置（`PDF_*`）/ 主系统自动注入（`OCR_*`）/ 可选覆盖（模型权重与解释器路径）/ 代码常量"四组，至少补齐 `PDF_OCR_ENABLED`、`PDF_OCR_PACKAGE_DIR`、`PDF_OCR_STORAGE`、`PDF_MAX_*` 三项与 `PDF_JWT_*` 三项。

**N4-05　规模假设依据链缺中间变量；检索指标与"建立于表 2-6"的表述不严谨**
- 位置：`:242`（表 2-6）、`:1111`（表 6-3 月配额）、`:1166` 与 `:1173`（表 6-6 及其说明）
- 证据：需求文档 `:347-349` 的完整假设为"单机部署面向 **5～30 人团队**，日均识别量 50～200 页，文件存量按 1000 个文件、平均 30 页（共约 3 万页）规划"；表 2-6 只承接了后两项，漏掉用户规模。表 6-3 默认 500 页/用户/月 ≈ 16.7 页/日/用户，要凑出日均 200 页需约 12 个满额活跃用户——这个中间变量在设计中不存在，读者无法自行校验两数字是否冲突。另 `:1173` 称"以上为设计目标，建立于表 2-6 的规模假设"，而 `:1166` 的检索指标写"10 万页规模"；需求文档 `:1411-1412` 明确其验证方式是"按 3 万页实测外推并复测"，设计文档未写出"存量规模 ≠ 指标外推规模"这一区分。
- 判定：数字本身不矛盾（10 万页非文档杜撰，见第二节），但**依据链不完整**，容易被误读为指标基线自相矛盾或配额与吞吐量打架。
- 建议：表 2-6 补"5～30 人团队"与"10 万页为检索指标外推规模、非当前存量"两行；`:1173` 改为"页面类指标建立于表 2-6 存量假设；检索指标为 10 万页规模的外推目标，验证方式为按 3 万页实测外推并复测（尚未实测，见表 6-7）"。

**N4-06　附录 B 通配符索引无法逐图定位，与其自身承诺相悖**
- 位置：`:1263`、`:1265`、`:1262`
- 证据：`:1265` 称"表 B-1 给出各图对应的原始成图文件，便于按图号定位与版本更新"，但 `:1263` 用一行 `| 图 5-1 ～ 5-20 | … | ../../prototype_img/Snipaste_2026-10-29_*.png |` 覆盖 20 张图；正文 `:909`～`:1003` 实际有 20 个精确文件名。文件存在性校验显示 21 个路径中**仅该通配符路径不存在**，即按附录 B 给出的路径无法打开任何一张原型图。同类不一致：`:1262` 图 4-1/4-2/4-3 行只给第一个完整路径 `../media/image18.png`，后两个写成裸文件名 `image19.png`、`image20.png`。
- 影响：版本更新时无法由图号反查原图；与"图表索引"章节的功能定位不符。
- 建议：把图 5-1～5-20 展开为 20 行"图号 → 精确文件名"，或增列一张对照表；图 4-1～4-3 统一为完整相对路径。

**N4-07　Word 正稿图片超宽、静态目录无页码**
- 位置：`docs/design/系统设计文档_V1.0.docx`、`scripts/export_design_docx.py:154-158`
- 证据：量测得页宽 210.01 mm、左右页边距各 31.8 mm → 可用正文宽 **146.4 mm**。39 张 `inline_shapes` 宽度直方图为 `132.08 mm × 20`（原型图，`width="5.2in"`）与 `146.56 mm × 19`（`media/image*.png`，pandoc 默认按页宽），后者超可用宽度 0.16 mm，共 **19 张**。导出脚本只设置页面尺寸与边距，未对无显式宽度的图片做二次缩放。另 `word/document.xml` 中 TOC 样式段落 0、无点引导线、目录条目无页码，静态目录为普通段落；页脚 PAGE 域正常（见第二节）。
- 影响：Word 可能对超宽图自动缩放，造成与原型图宽度规则不一致；正式设计文档目录无页码，不便按页检索。
- 建议：导出脚本把 146.56 mm 组统一压到 ≤145 mm；目录改为带页码与点引导线的静态目录，或改用 Word 域目录（需在导出脚本中实现，本报告不代替实施）。

### P3：表述精度与格式一致性

**N4-08　2.1 系统边界与需求范围外清单未逐项对齐**
- 位置：`:168`；需求文档 `:202-208`
- 证据：需求范围外为"手写体识别、**竖排与无线框表格**、移动端与跨机分布式、公式与图表识别"；设计边界为"不实现手写体专项识别、**竖排与合并单元格表格还原**、数学公式与图表识别、移动端原生应用、多机分布式部署与消息中间件"，漏"无线框表格"；而 `:963` 又明确"无线框表格降级为按行聚类纯文本并标注未还原"。
- 判定：语义可自洽（降级不等于交付），但边界清单应能逐项对照需求范围外清单。建议边界补"无线框表格结构还原"。

**N4-09　表 6-3 退避序列漏第 3 次**
- 位置：`:1107`"最多 3 次，退避 15 s、30 s"
- 证据：`queue.py` 实际为 `cfg.retry_delay_seconds * 2 ** (job.attempts - 1)`，基数 15 s → 15 / 30 / **60** s。
- 建议：补"第 3 次 60 s"，或改为"按 15 × 2^(n-1) 指数退避，最多 3 次"。

**N4-10　附录 B 尾句与收尾句表述过满**
- 位置：`:1265`、`:1269`
- 证据：`:1265`"宽幅图按页宽等比缩放"与实际"原型图 5.2 in、media 图按页宽"两种规则不符；`:1269`"本文档为系统设计与维护的技术基线"与 1.1"未显式标注的条目为设计约定，不代表已经落地"并列时，易被读成验收基线。
- 建议：`:1265` 改为"图宽按导出脚本统一约束，需查看细节时放大原始成图"；`:1269` 改为"设计与维护的技术约定基线"。
