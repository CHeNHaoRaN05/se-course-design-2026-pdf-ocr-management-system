## 3. 本轮新发现

### T-P1 — 附录 A 的 NFR 追溯链不完整、编号不可对齐

需求文档实际有 **7 组 NFR**：`CMP(5) / LEG(5) / MNT(6) / PERF(11) / REL(7) / SEC(11) / USE(8)`，编号形如 `NFR-CMP-01`。
设计文档附录 A 只有 4 行：

| 现有行 | 问题 |
|:---|:---|
| `NFR-PERF / REL` | 组名简写而非编号；`REL` 未带 `NFR-` 前缀；把两组并入一行 |
| `NFR-SEC` | 组名简写（应为 `NFR-SEC-01～10`） |
| `NFR-USE` | 组名简写（应为 `NFR-USE-01～08`） |
| `NFR-MNT` | 组名简写（应为 `NFR-MNT-01～06`） |
| — | **完全漏追 `NFR-CMP-01～05`（兼容性）与 `NFR-LEG-01～05`（法务合规）** |

后果：
- `1.2` 术语表称「FR / NFR 用于附录 A 的追溯」，但 NFR 行无法与需求编号逐条对应，**追溯矩阵对非功能需求实质失效**。
- 兼容性需求（`NFR-CMP-01～04`：浏览器、操作系统、数据库、文件格式）在 2.2、6.4 有设计内容，法务合规需求（`NFR-LEG-01～04`：著作权提示、第三方许可、数据不出域）在 2.4 C-05、6.3 有部分内容，但都**没有建立追溯行**，无法证明已被覆盖。
- 附录 A「验证方式」列全为泛称（「接口测试」「权限矩阵测试」「安全测试与代码评审」），实际测试文件为 `test_auth.py` / `test_main_flow.py` / `test_share.py` / `test_ocr_contract.py` / `test_quota.py` / `test_share_model.py`，并无「权限矩阵测试」等命名用例，验证链不可核查。

### T-P2 — 需求裁剪未在文档声明

`NFR-CMP-04` 要求「图片支持 PNG / JPG / BMP / TIFF」；设计文档表 4-4 与表 4-20 只列 `application/pdf / image/png / image/jpeg`，2.1「系统边界」的范围外清单也未提及 BMP / TIFF。
代码实况：`core/media.py:29-30` 按真实内容判断类型，`media_type = "image/png" if image.format == "PNG" else "image/jpeg"`，即 Pillow 能打开的 BMP / TIFF 会被**统一标注为 `image/jpeg`** 而非拒绝。

这属于「实现与需求口径有差异且文档未说明」，不是代码错误，但设计文档作为需求到实现的桥梁，应在系统边界或媒体类型枚举处明确说明支持范围与类型归一规则。

### T-P2 — 数据字典字段说明的 4 处细节偏差（前两轮未做字段级抽查）

| 位置 | 文档表述 | 代码事实 |
|:---|:---|:---|
| 表 4-4 `:550` | `storage_key` …「禁止 `..`」 | 4.3 已修正为「以规范化路径是否越出存储根目录判定」（`media.py:22-26` 用 `resolve()` + `is_relative_to()`），数据字典未同步，同一实现两种口径 |
| 表 4-4 `:552` | `sha256` …「用于去重与秒传」 | `files/service.py:47-48` 仅把摘要写入 `File`，全仓无去重、秒传或 `dedup` 逻辑。**「秒传」是不存在的能力** |
| 表 4-4 vs 表 4-13 | `files.owner_id VARCHAR(32)` / `ocr_files.owner_id VARCHAR(128)` | 两者代码确实分别是 `String(32)` 与 `String(128)`，文档各自正确；但 C2 契约称「镜像 8 个字段」而未说明**同名字段长度不一致**，长度 >32 的归属者标识在镜像侧可写入、主系统侧会溢出，属潜在契约隐患 |
| 表 4-14 `:671` | `created_at / finished_at | DATETIME | 可空 | 创建 / 终态时间` | `db.py` 中 `created_at` 为 `mapped_column(DateTime, default=now)`，由 ORM 必填；与「终态才写」的 `finished_at` 语义不同，合并成一行并统一标「可空」不准确 |

附带：表 4-10 `:615` 把「保留 180 天」写在字段说明里，而 4.3/6.5 已明确该保留期为设计目标。1.1 的新规则已兜底（未标注 = 设计约定），但同一事实在字典与运维章节的呈现仍不齐。

### T-P2 — F1 上传流程的状态码与实现不完全一致

3.2.3（F1）与 5.3.3 描述「超限分别返回 413 / 422 / 415」。实际：
- 主系统 `/api/v1/files`：`core/media.py:71-72` 抛 `MediaError("upload_size_limit")`，`modules/files/service.py:44-45` 统一 `raise bad_request(str(exc))` → **422**；类型/内容不合法同样走 `MediaError` → 422。主系统上传路径**不产生 413 或 415**。
- 413 仅存在于 OCR 模块独立上传接口（`ocr_service/api.py` 的 `HTTPException(413, "File exceeds upload limit")`）；415 仅由 `core/errors.py:unsupported()` 提供，上传链路未调用。
- 507 在业务代码中 0 命中（已在表 6-7 标为未实现）。

按 1.1 的新规则，F1 未标注不等于「已实现」，因此不构成误导性事实错误；但 3.2.3 是「处理流程与关键算法」章，读者自然按运行行为理解，建议把三种状态码改成实际映射或明确标注为设计侧错误语义。

接口详细规格（请求/响应 schema、示例、幂等性、限流）、独立测试设计章节、监控采集口径与告警阈值、风险登记（等级×影响×责任人×时限）、「概要设计说明书」与详细设计深度的定位不符、表 3-4 架构决策无编号且不纳入附录 A 追溯——自第一轮提出后**三轮均未变化**。按第二轮建议，这些属于扩写型工作，应在标注与追溯收口后再评估，本轮不重复展开。
