## 一、总体结论

**未发现新的 P0 事实错误。** 本轮把文档中最容易虚报的数字做了机械复核，结果与代码高度吻合：接口总数与五组分布逐条对上、55 个表号与 39 个图号全章连续、Word 目录与 Markdown 目录逐条一致、状态枚举与请求约束与实现一致。这说明前三轮收口后的"事实层"已比较扎实。

但换到**规范性条款与运行时分支**后，发现 **2 项 P1**：一是 3.1.5 的"唯一例外是五份契约"与文档自身承认的"第六个隐式契约"及代码相冲突；二是检索接口在 OCR 未挂载时存在第三种 `backend` 取值与空集降级，接口设计与运行降级章节均未声明。另有 **2 项 P2**（静态目录层级倒置、绝对化措辞掩盖已知 P0 缺陷）与 **3 项 P3**（逐字重复句、`见表 6-7` 引用密度、表 5-3 / 5-4 分组口径）。

结论：文档可作为**设计约定基线**继续使用；若作为接口联调与变更评审依据，需先收口 N5-01、N5-02。前三轮提出的扩写型充分性缺口（接口逐条详细规格、独立测试设计章节、监控采集口径、风险登记表、文档定位由"概要设计"改为"详细设计"）本轮仍未解决，也不擅自扩写。

## 三、问题清单

### P1：契约与规范条款风险

**N5-01　架构约束「唯一例外是五份契约」与文档自身及实现冲突**
- 位置：`:326`（3.1.5 模块依赖规则）、`:231`（表 2-5 C-10）；对照 `:354`、`:865`
- 证据：`:326` 写"后端三条功能线的业务模块之间禁止直接引用，**唯一例外**是下列五份契约规定的调用"；`:231` 写"后端业务模块之间**仅通过五份契约**协作"。但同一文档 `:354` 写"检索服务以裸 SQL 直查 `pdf_text_index` 是一处跨模块直接依赖，其字段集合视为隐式契约"；`:865` 写"跨模块直接依赖：`search/service.py` 以裸 SQL 直查 `pdf_text_index`……变更须与 C1～C5 同级别评审"。代码侧 `search/service.py:17` 在函数内 `from ..ocr.bridge import is_ready`，`:29` 以裸 SQL `FROM pdf_text_index AS t JOIN files` 直查 OCR 侧表。
- 判定：文档既承认存在第六个"隐式契约"并要求"与 C1～C5 同级别评审"，又宣称五份契约是"唯一例外 / 仅通过"，规范性条款自相矛盾。3.1.5 同时规定"契约内容变更须先修订契约定义并通过评审，再修改实现"，读者无法判定这一隐式契约是否受该流程约束——影响的是**变更评审流程的执行**，不只是措辞。
- 建议：`:326` 改为"除下列五份显式契约外，另有一处隐式契约：检索服务直查 `pdf_text_index`（见 4.4、5.6），其字段集合变更按同级别评审"；表 2-5 C-10 改为"通过五份显式契约与一处隐式契约协作，前端跨功能引用列为待收敛项"。

**N5-02　检索接口的降级分支与 `backend` 第三取值未声明**
- 位置：`:423`（3.2.3 检索流程）、表 5-4（`:1054`）、`:1127`（6.1 运行降级）
- 证据：`search/service.py:17-20` 在 `bridge.is_ready()` 为假时直接 `return "ocr_not_ready", []`；`search/router.py:26-27` 以 `response_model=dict` 原样返回 `{"backend": backend, "items": items}`，无取值校验。`bridge.py` 的 `_ready` 由 `mount_ocr` 在挂载成功/失败时设置——即 OCR 未挂载（6.1 已列为部署场景）时必然走该分支。文档 `:423` 只写"响应以 `backend: mysql_ngram | substring` 标明实际检索后端"；`:1127` 只说"`/ocr-host/*` 统一返回 409，主系统其余功能可用"，未说明 `/search` 此时返回 200 + 空集 + 第三取值。
- 判定：按文档只处理两种 `backend` 的客户端遇到 `ocr_not_ready` 会误判；且"主系统其余功能可用"掩盖了检索实际返回空结果的事实，与 6.1 想表达的降级语义不符。附带提示：`ocr_service/schemas.py:111` 的 `SearchOut.backend` 是 `Literal["mysql_ngram", "substring"]`，虽用于 OCR 侧 `/ocr/search`（该侧无此分支），仍建议在代码侧一并核对；本报告只审文档，不代替代码改动。
- 建议：`:423` 补 `backend: mysql_ngram | substring | ocr_not_ready`，说明第三值表示 OCR 未挂载且 `items` 为空；6.1 运行降级补"未挂载时 `/search` 返回 `ocr_not_ready` 与空结果集，前端应提示识别能力不可用，而非报告检索无命中"。

### P2：专业性与内容充分性

**N5-03　静态目录层级倒置，14 个三级标题不可检索**
- 位置：`:40-88` 静态目录；Word 正稿目录同为 51 条
- 证据：目录收录 6 个章标题、全部二级标题与 **16 个四级标题（5.3.1～5.3.16，覆盖率 100%）**，但 **14 个三级标题（3.1.1～3.1.5、3.2.1～3.2.4、4.1.1～4.1.5）收录率为 0**。这些三级节承载设计目标与原则、架构决策与权衡、跨模块契约、处理流程与关键算法、数据字典、JSON 字段结构、状态枚举与完整性约束——都是设计文档中最需要按目录定位的实质内容。
- 判定：四级全收、三级全不收，层级逻辑不自洽；前四轮只校验了"目录条目是否有对应标题"（结果为 0 悬空），未反向校验"标题是否都在目录"，故此前未发现。
- 建议：把 14 条补齐（目录变 65 条），或明确改为"列到三级、5.3.x 作为界面清单特例"并说明理由。`scripts/export_design_docx.py` 按 `Compact` 目录段落文本匹配 Heading 自动挂书签与 `PAGEREF`，补条目后页码域会自动覆盖，无需改脚本。

**N5-04　绝对化措辞掩盖已知缺陷，与 1.1 的三态标注口径冲突**
- 位置：`:1150`、`:1186`、`:465`、`:96`
- 证据：
  - `:1150`"租约、条件更新与 `SKIP LOCKED` **保证**任务不丢失且不被并发处理"、`:1186`"领取与提交均为条件更新，**保证**同一任务不被并发处理"——但表 6-7 的 **P0** 明确写"MySQL 下队列锁与校对接口依赖'把字段更新成原值'的条件更新受影响行数……生产使用 MySQL 前必须修复，否则结果无法提交、校对持续返回 409"。同一文档既"保证"又"必须修复"，是承诺冲突。
  - `:465`"审计日志只提供记录与查询，从对象模型上**保证不可篡改**"——实现只是应用不提供写接口，`Audit` 表无数据库级只追加约束，属过度承诺。
  - `:96`"本文档覆盖系统的**全部**设计要素……**均**在文中给出"——与本报告及前三轮持续指出的充分性缺口（接口详细规格、独立测试设计、监控口径、风险登记）不符。
- 建议：把"保证"改为"按设计应能 / 旨在"，并在 `:1150`、`:1186` 就近标注"MySQL 下该机制受表 6-7 P0 限制"；`:465` 改为"应用不提供修改与删除接口"；`:96` 改为"本文所列设计要素均在文中给出"，删去"全部"。

### P3：表述精度与冗余

**N5-05　逐字重复句**
- 位置：`:417`（F6 规则表格还原算法）与 `:964`（5.3.8 界面说明）
- 证据：量化检测 333 个长句（≥ 18 字）中，**唯一 1 处**完全重复："无线框表格降级为按行聚类纯文本并标注未还原"。全篇精确重复率很低，但这一句是流程说明与界面说明整句照搬。
- 建议：其中一处改为引用，如"按 5.3.8 的降级口径处理"。

**N5-06　`见表 6-7` 引用密度过高；命名同一性表述过满**
- 位置：全文 17 处 `见表 6-7`（表 6-7 仅 9 行）、`:96`
- 证据：17 处引用分布在 `:231, 322, 366, 838, 842, 844, 906, 970, 1064, 1068, 1125, 1135, 1186, 1196, 1198, 1247, 1250`，平均每 77 行一次，正文被反复打断。另 `:96` 称"文中模块名、表名、接口路径与类名与实现采用同一命名"，而表 5-4 用 `{id}` / `{n}` / `.../retry` 等简写，代码中为 `{file_id}` / `{page_no}` / 完整路径。
- 建议：在 1.1 实现状态标注处集中声明一次"各项实现状态统一见表 6-7"，正文仅保留确有对应条目的引用；`:96` 改为"采用可对应的命名，清单中路径参数作简写"。

**N5-07　表 5-3 与表 5-4 分组口径不一致且未说明**
- 位置：`:1031-1040`、`:1042-1056`
- 证据：表 5-3 按**前缀**把 `/search*` 归入"OCR 宿主能力与检索"（7 个 = ocr-host 5 + search 2）；表 5-4 按**用途**把 `GET /search`、`/search/suggest` 放进"导出与检索"组，与 `/ocr/*` 接口混列。两表的组名相似但划分维度不同，读者容易把表 5-4 的组名当作表 5-3 的统计分组去复核 59 这个数字。
- 建议：表 5-4 标题补"按用途分组，与表 5-3 的前缀统计口径不同"，或把组名改为不带"统计"含义的名称。
