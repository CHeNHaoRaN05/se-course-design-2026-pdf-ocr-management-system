## 二、第七轮发现与修复

审查方式：机械解析 7 个主系统 `router.py` + `ocr_service/api.py` 的装饰器 `status_code`、`response_model` 与 `Depends(...)` 依赖，与 5.5 / 表 5-4 / 6.2 / 表 6-4 逐项比对。

1. **（P1）6.2「业务代码不自行抛出未包装的 HTTP 异常」与实现不符**：仓库共 28 处直接 `raise HTTPException(...)`，其中 `core/principal.py` 7 处（401 / 403）、`ocr_service/api.py` 21 处（413 / 422 / 409 / 404）。改为分别说明主系统业务模块经 `core/errors.py` 包装、鉴权层与独立 OCR 模块直接抛 `HTTPException`，二者对外均只暴露 `detail`；并注明 `unsupported(415)` 已定义但当前未被调用（全仓 0 次调用）。
2. **（P2）6.2 状态码列表与表 6-4 不齐**：正文列 8 个状态码，表 6-4 含 507、F1 提到 415。补齐 413 限定为「仅 OCR 独立上传接口」、415「当前未触发」、507「设计目标，当前未实现」。
3. **（P2）表 6-4 的 413 行与第四轮已修的 F1 冲突**：表中泛写「文件超过 20 MiB → 413」，而 F1 明确主系统上传校验失败统一 422。改为注明 413 仅适用于 OCR 独立上传接口并回指 3.2.3 F1。
4. **（P2）5.5「分页参数统一 `limit / offset`」过度概括**：全仓仅 2 处 `limit: int = Query(...)`（`GET /files`、`GET /search`），其余列表接口返回全量。改为限定说明。
5. **（P2）表 6-3 磁盘阈值行失去状态标注**：第五轮精简 `见表 6-7` 引用后，未实现的 507 以「运行参数」面貌呈现（代码中 507 出现 0 次）。补「设计目标，当前未实现，见表 6-7」。
6. **（P3）表 5-4 状态码信息不全**：补 `POST /ocr/jobs/{id}/retry`（202），并说明创建类接口默认 201、删除类接口默认 204。

复核确认无误：管理员接口确用 `require_admin`、写接口用 `require_editor`、`GET /share/token/{token}?code=` 无 JWT 依赖且参数名一致、`core/errors.py` 5 个函数与文档一致、表 4-10 超长枚举单元格所在表格 4 列合计 139.68 mm < 可用 146.4 mm 且 `autofit=False` 未溢出。

1. **表 2-4 OCR 工具名不准**：写 `opencv-headless`，实际锁文件 `environment-service-lock.txt` 为 `opencv-python` 与 `opencv-python-headless` 并存（表 6-7 P1 已记录该风险）。改为两个准确包名并回指 P1，补 `openpyxl 3.1.5`。
2. **表 2-4 测试口径未同步第六轮**：写「主系统 72 项、OCR 模块 10 项」「OCR 测试未纳入 CI」，与 6.5 新口径不一致。改为区分本机 72 / 10 与 CI 实际 67 项，并说明主系统契约用例也未纳入 CI、口径见 6.5。
3. **表 6-7 P3 建模源码表述与仓库矛盾**：写「PlantUML 文本源码目录尚未建立」，而仓库 `uml/` 有 7 个 `.puml`、`docs/er-diagram.mmd` 真实存在——但它们对应**需求文档**图。改为「本设计文档 39 张图的可复现建模源码尚未建立」，并说明现有源码的归属。

复核确认无误：`requirements.txt` 与 `frontend/package.json` 的全部版本与表 2-4 一致；设计文档引用的 72 个 FR 编号与 51 个 NFR 编号**全部**存在于需求文档、附录 A 覆盖全部 17 个需求组；章节引用、F1～F10 流程编号引用 0 悬空。
