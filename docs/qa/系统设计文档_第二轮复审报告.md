## 2. 新发现（按严重度）

### N-P0 — 修订引入的逻辑矛盾：三态规则的默认项与标注覆盖率不匹配

`1.1 :84` 新增：「**凡未显式标注者默认为已实现**；设计目标与待办以表 6-7 为汇总清单」。
`5.3 :888` 同时声明本节为高保真原型、仅 5 个 React 页面已实现，但接的是「本节中与实现不一致的能力以实现状态标注（见 1.1）与表 6-7 为准」。

对抗性核验结果：

- **16 个 5.3.x 小节中，14 个完全没有状态标注**（仅 5.3.9、5.3.16 含标记）。按 1.1 的默认规则，这 14 节的描述全部被推定为「已实现」。
- 其中明确与代码相悖的陈述包括：`5.3.4 :914`「到期由清理任务按 C5 顺序物理清除」（清理任务不存在，`C5-lifecycle.md:30-33` 列为 W7 待办）；`5.3.5 :922`「缩略图侧栏、目录大纲、页内搜索高亮、书签与阅读位置记忆」（`ReaderPage.tsx:79` 明写「W7 待补」）；`5.3.13 :976`「只追加不可修改、保留 180 天」（无数据库层约束、无定时任务）；`5.3.12 :970` 统计看板图表、`5.3.11 :964` 角色权限矩阵等原型内容。
- `6.2 :1120`「审计日志只追加并保留 180 天」同样未标注，按默认规则被读成已实现，而 `6.5 :1168` 又把同一保留期标为「设计目标，当前未实现」——**同一事实在同一文档内两种定性**。
- 「表 6-7 为汇总清单」不成立：表 6-7 仅 11 行，未覆盖 6.4 表 6-6 的 10 项性能指标、未覆盖上述 14 个原型小节、未覆盖 4.3 的容量策略。

**影响**：这是本轮最严重问题。修订前读者至少不会按「默认 = 已实现」去读；修订后文档自己给出了一条会把大量未实现内容判定为已实现的规则。`5.3 :888` 的「为准」表述与 1.1 的默认规则互相覆盖，未形成可执行的判据。

## 3. 仍存优点（复审确认）

1. 核心机制与代码一致：进程划分与同进程挂载、数据库表即队列（租约 + CAS + `SKIP LOCKED`）、页级 `revision` 乐观锁、ngram `ddl_if` 与 LIKE 降级、任务 7 态、5 种导出与公式注入防护、`safe_path` 目录逃逸判定、C1～C5 契约，本轮抽查未发现新的事实偏差。
2. 数字可核查性提升：59 接口统计口径、72 项测试、218 MB 权重、20 万轮哈希均有代码或仓库依据。
3. 工程诚实性仍在：6.4 标注「以上为设计目标」、表 2-6 列「尚未验证」、表 6-7 主动列 P0 MySQL 缺陷并前置到 3.1.4。
4. 封面基础信息、页码、图表编号与索引、文档独立性、目录结构在两轮修订中均未被破坏。
