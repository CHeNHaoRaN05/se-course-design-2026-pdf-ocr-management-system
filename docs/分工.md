## 0.2 数据库 Schema（最大扯皮点）

`backend/scripts/init_db.py:14` 用的是 `Base.metadata.create_all()`，**不会迁移已存在的表**（脚本注释已写明）。

三人并行加字段 → 各人本地库结构分叉 → 合并后别人机器上跑出 500，且报错不指向根因，极难排查。

**规则：**

1. **W5 结束前定稿冻结** schema，陈牵头补齐缺口（目前 `share_link` 表在 `docs/DATABASE.md` 已设计，但 `backend/models/` 里**没有对应模型**）
2. 冻结后新增/修改字段必须走 PR，合并人在 PR 说明中标注「需重建开发库」
3. 全组执行 `.\scripts\reset_dev_db.ps1`
4. 演示前一周停止一切 schema 变更

## 0.4 Python 版本

| 进程 | 版本 | 原因 |
|---|---|---|
| 主系统 API | 3.12 / 3.13 / 3.14 均可 | `api.py` 顶层不 import paddle |
| OCR worker | **必须 ≤ 3.13，统一用 3.12** | `paddlepaddle==3.0.0` 最高只提供 cp313 wheel，无 cp314 |

`requirements.txt` 主组锁的是 3.12 版本组；本机 `.venv` 是用文件末尾「Python 3.14 可用版本」装的备用组。**两者不是同一套版本**，交付前必须统一，否则本地与部署漂移。

## 0.5 三个环境变量必须一致

| 变量 | 必须与谁一致 |
|---|---|
| `PDF_DATABASE_URL` == `OCR_DATABASE_URL` | 同一个库 |
| `PDF_STORAGE_DIR` == `OCR_STORAGE` | 同一目录，否则 worker 读不到文件 |
| `PDF_JWT_SECRET` == `OCR_JWT_SECRET` | 同一把密钥，短于 32 字符直接抛错 |

Python 版本**允许不同**（主系统 3.14 + worker 3.12），这是原设计的进程隔离带来的好处。

## 0.8 统一约定

- 后端：`snake_case`，路由前缀 `/api/v1/`
- 前端：组件 `PascalCase`，变量/函数 `camelCase`
- 所有中文文档 UTF-8
- 分页参数统一 `limit` / `offset`

### 10.4 ⚠️ 两份 `media.py` 的同步义务

`backend/core/media.py` 的 docstring 明确写了：OCR 模块为了「独立可部署」自带一份 `media.py`，
**两者输入输出契约一致（media_type / page_count / sha256 / size），属有意重复**。

**任何一侧修改校验规则，都必须同步另一侧**（契约 C2）。
例如岳提高了页数上限而黄没同步 → 上传成功但 worker 渲染失败，且报错指向 OCR 侧，极难定位。
