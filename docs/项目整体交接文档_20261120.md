## 第一部分 技术架构与代码

### 1.1 系统组成

系统由 **3 个进程 + 2 个外部依赖**构成：

| 进程 / 依赖 | 技术栈 | Python | 端口 | 职责 |
|---|---|---|---|---|
| 主系统 API | FastAPI + SQLAlchemy + Uvicorn | 3.12 基线（3.14 用备用依赖组） | 8000 | 用户权限、文件管理、PDF 显示、检索、分享；OCR 模块接口挂载在同一进程内 |
| OCR worker | `ocr_service` + PaddleOCR CPU | ≤ 3.13（统一 3.12） | 无 | 轮询数据库领取任务、识别、回写页结果与全文索引 |
| 前端 | React 18 + Vite 5 + pdf.js 4 | — | 5173 | 页面渲染；`/api` 代理到 8000 |
| 数据库 | SQLite（演示/开发）、MySQL 8（可选） | — | 3306 / 文件 | 业务数据与任务队列 |
| 文件系统 | 共享存储目录 | — | — | 原文件、页 PNG、导出缓存；主系统与 worker 必须指向同一目录 |

**关键点：OCR 模块不是独立 Web 服务。** `ocr_service.install(app, settings)` 把 OCR 路由挂进主系统 FastAPI 实例，同进程、同端口、同 JWT；真正独立的只有不监听端口的 worker，它通过数据库与共享存储与主系统通信。

三条一致性必须满足（否则全链路不通）：

| 项 | 要求 | 不满足的症状 |
|---|---|---|
| 数据库 | `PDF_DATABASE_URL == OCR_DATABASE_URL` | 任务永远停在 `queued` |
| 存储目录 | `PDF_STORAGE_DIR == OCR_STORAGE` | worker 读不到文件 |
| JWT 密钥 | `PDF_JWT_SECRET == OCR_JWT_SECRET`（≥32 字符） | OCR 接口全部 401 |

两侧 Python 版本允许不同，这是进程隔离带来的设计优势。

### 1.3 分层与依赖规则

- 前端 → HTTP `/api/v1` → 后端业务模块 → 底座与模型。
- 三条线业务模块之间**禁止直接 import**，仅通过 `core/` 底座或契约 C1–C5 协作。
- 唯一隐式契约：检索服务 `search/service.py` 用裸 SQL 直查 OCR 侧表 `pdf_text_index`——字段变更会直接让检索 500，且报错不指向根因，是最脆弱的一环。
- `core/principal.py` 是唯一鉴权入口，对外只暴露 `current_user` / `require_editor` / `require_admin` 三个依赖和 `Principal(user_id, role, is_admin)`；禁止绕过它自己查用户表。越权与资源不存在统一返回 404（避免资源探测）。

## 第四部分 接手操作指南

### 4.1 环境准备

1. 从 `docs/team/getting-started.md` 读取版本矩阵（已实测：Python 3.12、FastAPI 0.115.12、SQLAlchemy 2.0.41、pdfjs-dist 4.10.38、Vite 5.4.11 等）。
2. 主系统与 OCR worker 用**两个独立 Python 环境**：主系统任意 3.12/3.13/3.14（依赖分组见 `pdf_system/requirements.txt`）；worker 必须 ≤3.13（统一 3.12，Paddle 3.0.0 无 cp314 wheel）。
3. `pdf_system/.env.example` → 本机 `.env`，`PDF_JWT_SECRET` 用 `python -c "import secrets;print(secrets.token_hex(32))"` 生成；密钥、数据库、模型权重不得入库。
4. 模型权重按 `pdf_ocr_module/ocr_service/models/manifest.json` 下载并校验 SHA256（约 218 MB），不在仓库内。

### 4.2 启动顺序

```bash
# 终端 1：主系统（在 pdf_system/ 目录，SQLite 开发库）
python -m backend.scripts.init_db
python -m uvicorn backend.main:create_app --factory --host 127.0.0.1 --port 8000
curl -s http://127.0.0.1:8000/health     # 期望 {"status":"ok","ocr_mounted":...}

# 终端 2：前端（在 pdf_system/frontend/ 目录）
npm ci
npm run dev                              # 5173，/api 代理到 8000

# 终端 3：OCR worker（另开，独立 Paddle 环境）
# 先确保 OCR_DATABASE_URL / OCR_STORAGE / OCR_JWT_SECRET 与主系统一致
python -m ocr_service worker
```

从仓库根目录运行时相对存储路径会指向别处，主系统务必从 `pdf_system/` 目录启动。

### 4.3 验收流程（无 Paddle 权重亦可做）

1. 注册登录 → 改密 / 令牌续期 / 管理员改角色与禁用。
2. 上传 PDF → 校验（魔数/页数/大小/加密拒绝/同名序号）→ 列表与详情。
3. 在线阅读 → 翻页、跳页、缩放、书签与批注增删查。
4. **下载原文件**（PR #9 合入后）→ 管理分页与状态过滤 → 批量移动/打标/删除 → 合并/拆分。
5. 软删除 → 回收站 → 还原 → 彻底删除。
6. 创建分享（有效期/提取码/允许下载）→ 游客 token 只读访问与下载 → 撤销后立即失效。
7. 建 OCR 任务 → 查进度/取消/重试 → 按页结果 → 导出（有识别结果时）→ 关键词检索与 suggest。
8. 跑测试：03 线按 CI 原命令 `pytest backend/tests ../pdf_ocr_module/ocr_service/tests -q`；02 线在 `feat/02` 提交上跑后端/前端单测/e2e/`test:live`。

### 4.5 交接判断原则

- 共享鉴权、数据库 schema、OCR 生命周期与配额结算是跨模块接口，改动前先核对 `pdf_system/docs/contracts/` 与目标代码，走 PR 评审。
- 开发库与展示库不可混同；老账本、孤立 OCR 任务与清理策略需单独核对。
- 需求/设计文档中的历史状态与接口计数若与目标提交冲突，以代码与实测为准并记录差异，不填造"已完成"。
- 本文所有远端状态均有日期（2026-11-20）；接手后新提交、CI、PR、分支保护变化须补日期、SHA 与原始证据再更新本文。
